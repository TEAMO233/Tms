# 实施计划：透明中转「运维信号板」

## 任务 1：实现前基线与页面边界

1. 确认当前工作区的既有改动不属于本任务，实施时只触碰 `vite-frontend/src/pages/transparent-relay.tsx`。
2. 使用已选视觉参考和 Product Design image-to-code 约束，保留现有 API、类型、路由和 AdminLayout。
3. 记录当前前端构建基线；若环境依赖不可用，记录阻塞原因，不扩大改动范围。

## 任务 2：增加页面内派生视图数据

1. 从 `relays` 派生 `l4Relays` 与 `udpQuicRelays`，统一把 `relayType === "udp_quic"` 作为协议中转判定。
2. 从同一列表派生总数、类型数量、应用失败数量和暂停数量，摘要项只读且不可点击。
3. 保留 `relayDisplayName`、`protocolText`、`relayTypeChip`、`statusChip` 和现有 loading 状态，不复制业务判断。

## 任务 3：重排页面主体为运维信号板

1. 将现有头部动作改为响应式的标题 + 操作区，五个按钮继续绑定原处理函数和 loading。
2. 保留 warning Alert 文案并压缩其垂直占用。
3. 新增四项摘要 strip，显示真实派生数据，不改变请求或 API。
4. 将规则列表拆为 L4 与 HY2/TUIC 两个分组 surface；使用对齐的规则行和轻量分隔线，避免卡片嵌套与重复留白。
5. L4 规则行保留名称、入口、目标、协议/类型、状态、错误和编辑/暂停恢复/节点状态/删除操作。
6. HY2/TUIC 规则行保留入口、协议、落地、状态和当前指引，不渲染不适用的 L4 操作。
7. 没有任何规则时显示现有空状态文案；单个分组为空时显示克制的分组空提示，不伪造数据。

## 任务 4：响应式、可用性和视觉细节

1. 宽屏使用多列对齐规则行；`lg` 以下切换为纵向字段块，避免固定宽度和横向溢出。
2. 长规则名、IP:port、落地名称和 `lastError` 使用 `min-w-0`、安全换行/截断及可读的等宽字体。
3. 操作组保持稳定顺序和清晰中文标签；必要图标仅复用现有图标组件，不新增 SVG 或依赖。
4. 保持 HeroUI 语义色和当前皮肤背景，不修改全局样式文件。
5. 弹窗 JSX 只做必要的窄屏滚动和布局适配，表单字段、校验和提交逻辑保持不变。

## 任务 5：验证与设计 QA

1. 运行目标页面 ESLint/TypeScript 检查及 `cd vite-frontend && npm run build`。
2. 启动前端并在与视觉目标接近的宽屏视口检查首屏；再检查窄桌面和移动视口。
3. 手动验证：刷新、复制聚合订阅、一键添加所有、新增、编辑、暂停/恢复、节点状态、删除，以及三个创建/状态弹窗的打开、loading、错误/成功反馈。
4. 使用原始截图和选定视觉目标对照页面层级，重点检查摘要、分组、类型标签、状态和错误的可见性。
5. 按 Product Design image-to-code 要求生成根目录 `design-qa.md`；只有 `final result: passed` 才能交付。

## 任务 6：交付边界

1. 汇总只涉及透明中转页面的文件变更和验证结果。
2. 不提交、不覆盖工作区中与本任务无关的 `.agents/`、`.codex/`、其他 Trellis 任务或既有用户改动。
3. 若需要提交，使用本任务专用提交，不包含其他任务内容；远端推送需等待用户明确要求。
